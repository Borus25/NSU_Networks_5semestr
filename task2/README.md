# Передача файлов по TCP

Клиент и сервер на Go для передачи произвольного файла по TCP с измерением скорости приёма. Используется собственный бинарный прикладной протокол.

Сервер принимает несколько клиентов конкурентно, сохраняет файлы в `uploads` и сообщает результат сохранения. Клиент считает передачу успешной только после получения положительного ответа сервера.

## Требования

- Go 1.24 или новее: сервер использует `os.OpenRoot`.
- Доступное TCP-соединение между клиентом и сервером.
- Право создавать каталог `uploads` и записывать в него файлы.
- Достаточное свободное место на сервере.

Внешние Go-зависимости не требуются. Для приведённых команд тестирования используются Linux и Bash.

| Файл | Назначение |

## Сборка

Все следующие команды выполняются из `Networks/task2/` в существующем Go-модуле:

```bash
mkdir -p bin

go build -o bin/task2_server ./server/cmd
go build -o bin/task2_client ./client/cmd
```

Собирать нужно каталог пакета, а не отдельный `main.go`.

Проверки исходного кода:

```bash
go fmt ./client/cmd ./server/cmd
go vet ./client/cmd ./server/cmd
```

Не добавляйте вложенный `go.mod`, если проект уже использует общий модуль `Networks`. Для самостоятельного размещения `task2` вне существующего модуля сначала выполните `go mod init tcpfile` в его корне.

## Локальный запуск

В первом терминале:

```bash
./bin/task2_server 9000
```

Во втором терминале, также из `task2`:

```bash
printf 'TCP transfer test\n' > hello.txt
./bin/task2_client 127.0.0.1 9000 ./hello.txt
```

Синтаксис сервера:

```text
./bin/task2_server <port>
```

Синтаксис клиента:

```text
./bin/task2_client <server-host> <server-port> <file-path>
```

Путь к файлу может быть абсолютным или относительным. Порт должен находиться в диапазоне 1–65535.

При успехе клиент выводит подтверждение сохранения и завершается с кодом `0`. При ошибке — выводит причину и завершается с кодом `1`.

## Запуск на разных компьютерах

1. Подключите компьютеры к сети, в которой разрешены соединения между ними.
2. Запустите сервер на первом компьютере.
3. Узнайте его адрес на активном сетевом интерфейсе.
4. Запустите клиент на втором компьютере с этим адресом.

На сервере:

```bash
ip -br -4 addr
./bin/task2_server 9000
```

На клиенте, если адрес сервера `192.168.1.42`:

```bash
./bin/task2_client 192.168.1.42 9000 ./hello.txt
```

```text
Клиент                         Сервер
192.168.1.57                   192.168.1.42
     |                              |
     +------ TCP, порт 9000 ---------+
```

Не используйте `127.0.0.1` для другого компьютера: это адрес самого клиентского компьютера.

Если соединение блокирует firewall, разрешите входящий TCP-порт сервера в соответствии с политикой своей сети. Не отключайте firewall целиком.

## Проверка через ngrok

Для этого бинарного протокола нужен TCP-туннель, а не HTTP/HTTPS endpoint.

На компьютере сервера:

```bash
./bin/task2_server 9000
```

В другом терминале того же компьютера:

```bash
ngrok tcp 9000
```

Пример вывода, не реальный адрес проекта:

```text
Forwarding tcp://1.tcp.ngrok.io:12345 -> localhost:9000
```

Для такого примера клиент запускается так:

```bash
./bin/task2_client 1.tcp.ngrok.io 12345 ./hello.txt
```

Используйте хост и публичный порт из своего вывода ngrok. Публичный порт не обязан совпадать с локальным `9000`.

Доступность TCP-endpoints зависит от условий аккаунта ngrok. Если сервис требует верификации или сообщает об ограничении, следуйте его текущим условиям. Не публикуйте сервер надолго: в приложении нет аутентификации.

## Прикладной протокол

Одно TCP-соединение используется для передачи одного файла. Все числовые поля заголовка кодируются в Big Endian.

### Запрос клиента

| Поле | Размер | Содержание |
|---|---|---|
| `nameLen` | 2 байта | Беззнаковое `uint16`, длина имени в байтах |
| `fileSize` | 8 байт | Беззнаковое `uint64`, размер файла в байтах |
| `name` | `nameLen` байт | Имя файла в UTF-8 |
| `content` | `fileSize` байт | Содержимое файла |

```text
[ nameLen: 2 ][ fileSize: 8 ][ name: N ][ content: S ]
```

Ограничения:

- Имя: от 1 до 4096 байтов UTF-8.
- Размер: от 0 до 1 000 000 000 000 байтов; 1 ТБ здесь трактуется в десятичном смысле.
- Имя не может быть `.` или `..` и не может содержать `/`, `\` или NUL.
- Клиент передаёт только базовое имя файла, без пути.
- Клиент принимает только обычные файлы.

TCP является потоком байтов: отдельные записи клиента не задают границы чтений сервера. Размеры полей задают границы на прикладном уровне.

### Ответ сервера

Ответ состоит из одного байта:

| Значение | Смысл |
|---|---|
| `0` | Файл принят, проверен и успешно сохранён |
| `1` | Ошибка при обработке передачи |

Описание ошибки и фактическое имя сохранённого файла в ответ не включены. Подробности доступны в серверных логах.

Успех подтверждается после проверки размера, `File.Sync` и успешного закрытия файла. Это не полная гарантия сохранности записи каталога при аварии ОС: каталог отдельно не синхронизируется.

При сетевом обрыве сервер не всегда может доставить статус ошибки. Если клиент не получил ответ, результат неопределён: файл мог быть сохранён, но подтверждение могло потеряться.

Сервер принимает ровно объявленный размер. Дополнительные байты не относятся к файлу и не обрабатываются как второй запрос.

## Сохранение файлов

`uploads` определяется относительно текущего рабочего каталога процесса, а не относительно расположения бинарника.

Сервер использует `os.OpenRoot` и файловые операции относительно открытого каталога. Файл создаётся с `O_CREATE | O_EXCL`, поэтому существующие файлы не перезаписываются.

Исходное имя используется, если оно не длиннее 200 байтов и свободно. Для занятого или более длинного имени выбирается вариант:

```text
upload-<случайный идентификатор>.bin
```

Порог 200 байтов — правило реализации для выбора имени, а не ограничение протокола. Фактическое имя отображается в логах сервера.

Незавершённый файл удаляется при штатной обработке ошибки. При аварийном завершении процесса, например SIGKILL, deferred-функции не выполняются и неполный файл может остаться.

## Конкурентность и скорость

Для каждого принятого соединения запускается отдельная горутина `serveConn`. Обработчик запускает дополнительную горутину статистики.

```text
Accept loop
   +-- serveConn(A) -> handleConn(A) -> статистика A
   +-- serveConn(B) -> handleConn(B) -> статистика B
   +-- serveConn(C) -> handleConn(C) -> статистика C
```

Счётчик принятых байтов для каждого клиента использует `atomic.Uint64`.

Статистика выводится примерно каждые 3 секунды и дополнительно при завершении, даже если передача длилась меньше 3 секунд. Планирование горутин может задержать периодический вывод.

- `received`: количество принятых байтов содержимого, без заголовка.
- `instant`: прирост счётчика, делённый на фактическое время с прошлого отчёта.
- `average`: весь счётчик, делённый на время с начала приёма содержимого.
- Единицы скорости: B/s, байты в секунду.

Финальная средняя скорость включает время завершения сохранения, в том числе `Sync` и `Close`. Счётчик приёма может быть больше количества записанных байтов, если запись на диск завершилась ошибкой.

Горутины планируются runtime Go и не соответствуют отдельным потокам ОС один к одному. Если учебное задание буквально требует POSIX threads или отдельные потоки ОС для клиентов, допустимость Go-модели нужно согласовать отдельно.

## Тайм-ауты

| Операция | Тайм-аут |
|---|---|
| Подключение клиента | 5 секунд |
| Чтение заголовка и имени сервером | 30 секунд суммарно |
| Очередное чтение содержимого сервером | 2 минуты |
| Очередная запись клиентом | 2 минуты |
| Ожидание результата клиентом | 2 минуты |
| Отправка результата сервером | 5 секунд |

Дедлайны чтения содержимого и записи обновляются перед операциями, а не ограничивают общую длительность передачи файла. Тайм-аут ожидания ответа клиента может истечь при очень долгом сохранении файла на сервере.

## Проверки

### Содержимое файла

На клиенте:

```bash
sha256sum hello.txt
```

На сервере:

```bash
sha256sum uploads/hello.txt
```

Хеши должны совпасть. Если сервер выбрал альтернативное имя, используйте имя из его логов.

### Пустой файл

```bash
touch empty.txt
./bin/task2_client 127.0.0.1 9000 ./empty.txt
```

Ожидается успешное сохранение файла размером 0 байтов.

### Большой файл

```bash
dd if=/dev/urandom of=large.bin bs=1M count=256 status=progress
./bin/task2_client 127.0.0.1 9000 ./large.bin
```

Если передача завершилась быстрее 3 секунд, промежуточного отчёта может не быть; финальный отчёт должен присутствовать.

### Несколько клиентов

```bash
./bin/task2_client 127.0.0.1 9000 ./large.bin >client1.log 2>&1 &
./bin/task2_client 127.0.0.1 9000 ./hello.txt >client2.log 2>&1 &
wait
cat client1.log client2.log
```

Ожидаются независимые соединения и отдельная статистика на сервере.

### Обрыв передачи

Запустите передачу достаточно большого файла и прервите клиент через Ctrl+C до её завершения. Сервер должен обработать ошибку, удалить неполный файл и продолжить принимать клиентов.

### Повторное имя

Передайте один и тот же файл дважды. Существующий файл не должен перезаписываться; новая загрузка должна получить альтернативное имя.

## Диагностика

Проверка слушающего порта на сервере:

```bash
sudo ss -ltnp 'sport = :9000'
```

Проверка маршрута на клиенте:

```bash
ip route get 192.168.1.42
```

Просмотр TCP-пакетов на сервере:

```bash
sudo tcpdump -ni any 'tcp port 9000'
```

| Симптом | Что проверить |
|---|---|
| `connection refused` | Запуск сервера, порт, адрес привязки, активный отказ firewall |
| Тайм-аут подключения | IP, маршрутизацию, firewall, изоляцию устройств |
| EOF при ожидании ответа | Логи сервера, совпадение протокола, тип ngrok endpoint |
| Нет файла с исходным именем | Рабочий каталог сервера и альтернативное имя в логах |
| Паника после ошибки `Listen` | Возврат из функции до использования listener и регистрации его `Close` |

## Ограничения текущей реализации

- Нет аутентификации, TLS и прикладной проверки хеша.
- Нет возобновления передачи, квот и ограничения числа клиентов.
- Размер проверяется, но SHA-256 автоматически не передаётся и не проверяется.
- Изменение исходного файла во время отправки не предотвращается; снимок файла не создаётся.
- Нет graceful shutdown с ожиданием всех обработчиков.
- `File.Sync` и обычные файловые операции не имеют собственного тайм-аута в этом коде.
- Для полного crash-safe сохранения нужна дополнительная работа с каталогом и стратегией публикации файла.

Используйте приложение в доверенной сети и не передавайте конфиденциальные данные через публичный endpoint без дополнительной защиты.

### Сохранённые недочёты server/main.go

При декомпозиции исходные тела функций не исправлялись:

- Ошибка `MkdirAll` создаётся через `fmt.Errorf`, но не выводится перед завершением.
- При ошибке `listener.Close` оборачивается `err`, а не `errLs`.
- После любой ошибки `Accept` цикл сразу повторяется без задержки или классификации ошибки.
